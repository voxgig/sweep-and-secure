# Review of sweep-and-secure (commit 99146c4), 22 Oct 2026

Scope: `sweep_and_secure.py` (1543 lines), `tests/` (34 tests, two fake tools), README.
Focus, as asked: robustness, error handling, never leaving the file system in a
broken state, test sufficiency, OS and Python version support.

## 1. Verdict

The design is sound and better than most tools of this kind: store first, remove
plaintext second; atomic writes; restore on dotenvx failure; verification that the
key really became `encrypted:`; private key file protected via `git check-ignore`.
The happy path works against the real TruffleHog 3.99.3 and dotenvx 2.38.2.

It is **not yet safe enough to call robust**. I reproduced six defects that lose or
corrupt a secret, leave plaintext behind while reporting success, leave the
private key exposed after a crash, or hand the application ciphertext in place
of its secret. All are fixable with local changes. The test
suite is well built but cannot see most of them because the dotenvx stand-in is
more forgiving than the real tool and no failure-path tests exist beyond three.
There is no CI, so the README's Windows/macOS/Python 2.7 claims are unverified.

## 3. Defects, most severe first

Severity key: **S1** secret lost/corrupted or plaintext left behind while reporting
success; **S2** inconsistent state or exposure after a failure; **S3** wrong
behaviour, recoverable; **S4** minor.

### S1-1. A value that cannot be quoted exactly is still removed from the source file

`quote_env_value()` falls back to `"..."` with `\\` and `\"` escaping for values
that contain `'` plus `$`, `"` or a backslash. Real dotenvx does not unescape `\"`
or `\\`, and it expands `$name` inside double quotes and backticks. Measured with
dotenvx 2.38.2:

| Original value | Stored by script | What `dotenvx get` returns |
| --- | --- | --- |
| `it's#a$ecret` | `"it's#a$ecret"` | `it's#a` |
| ``it's `x` "$y"`` | ``"it's `x` \"$y\""`` | ``it's `x` \"\"`` |

`encrypt_env_file()` returns `inexact` and a `[!!] check it with dotenvx get`
warning is printed, but `execute()` then rewrites the source file anyway. The
only correct copy of the secret is gone. (`dotenvx set` is no safer: it mangles
`pa$$word${HOME}` to `pa$/root`; the script's single-quote-first strategy is the
right idea, the fallback is wrong.)

Fix: in the fallback, escape `$` as `\$` (dotenvx honours it in `"` and `` ` ``);
treat any value containing `'` together with `"` or a backslash as not exactly
representable; for inexact items mark `status="manual"`, do not rewrite, and say
so. Then add a decrypt-and-compare step before any source rewrite:
`dotenvx get KEY -f FILE --overload` (or `decrypt --stdout` with the process
environment cleared, since dotenvx lets `os.environ` win over the file, see
section 6) must equal `item.secret`.

### S1-2. The same secret under two keys in one env file: the second key stays plaintext

`.env` = `DB_PASSWORD=<x>` and `POSTGRES_PASSWORD=<x>`. Items are de-duplicated
by `(path, token_bytes)`, so one item is produced and mapped to the first
matching key. Output: `Done: 1 secret(s) encrypted`, exit 0, and
`POSTGRES_PASSWORD=<x>` is still in the file. The post-check only looks at the
keys it encrypted.

Fix: for env files, create one item per entry whose value holds the secret
(or extend the job's key list with every such key). Add a post-condition that
no processed secret's bytes remain anywhere in a rewritten env file.

### S2-1. Unhandled exceptions mid-run leave an inconsistent state with no report

Two reproduced cases:

a) **Non-UTF-8 stdout plus `-v`.** Real dotenvx prints `◈` and `⛉`.
`say()` has encoding protection only under Python 2; under Python 3 with
`PYTHONIOENCODING=ascii` (or a cp1252 Windows pipe) it raises
`UnicodeEncodeError` inside `dotenvx_encrypt()` after dotenvx has rewritten
`.env`. Result: traceback, exit 1, secrets encrypted in `.env`, sources still
plaintext, `.env.keys` created and **not git-ignored**, no summary.

b) **Restore write fails** (fault-injected `ENOSPC` on the second write).
`encrypt_env_file()` catches the dotenvx error and calls `restore_file()`, whose
`write_bytes()` raises; nothing catches it. Traceback, and `.env` now contains
the staged plaintext copies of secrets that were only in source files before.

Fix: make `say()` never raise (on 3.7+ `sys.stdout.reconfigure(errors="replace")`,
otherwise encode with `errors="replace"`); wrap `execute()` so any exception
prints what was changed and what still holds plaintext; make `restore_file()`
failure a loud, specific message naming the file that now holds plaintext.

### S2-2. Interrupt or crash after encryption skips the private-key protection

`KeyboardInterrupt` between the env phase and the source phase (reproduced by
making `rewrite_source` raise) propagates to `__main__`, which prints
"Interrupted; nothing further was changed." By then `.env` is encrypted and
`.env.keys` exists, but `ensure_gitignore()` and the "TRACKED BY GIT" check never
run. For a tool whose purpose is keeping the key out of git this is the worst
place to stop silently. Same outcome in S2-1a.

Fix: add `.env.keys*` to `.gitignore` *before* the first dotenvx call (cheap,
idempotent), and run the keys-file/gitignore step in a `finally` once any
encryption happened. Make the interrupt message honest.

### S2-3. Re-runs are not idempotent: duplicate `KEY_2` entries

After `--no-rewrite` (a documented mode), an interrupted run, or a failed source
rewrite, the store holds `KEY=encrypted:...`. The next run cannot compare an
encrypted value with the plaintext it found, so `assign_names()` allocates
`AWS_ACCESS_KEY_ID_2`, stores the same secret twice and points the placeholder at
`_2`. Reproduced.

Fix: when the chosen name exists encrypted in the store, decrypt and compare
(the private key is local); on match reuse the key, on mismatch show the
collision in the listing and ask.

### S2-4. The printed `dotenvx run -f` advice does not decrypt nested env files

Found while verifying a Codex review comment, on the unmodified script with real
dotenvx 2.38.2. After the script encrypts `config/.env.production`, dotenvx has
written the private key to `<root>/.env.keys` (its cwd) and a `# -fk
../.env.keys` hint into the env file, and the script prints:

    dotenvx run -f config/.env.production -- <your command>

Measured from the project root: that command, `dotenvx get STRIPE -f
config/.env.production`, and the same `get` run from inside `config/` all return
the literal `encrypted:...` string. dotenvx 2.38.2 looks for `.env.keys` beside
the env file and does not follow its own hint. Only `-fk .env.keys` or a
`DOTENV_PRIVATE_KEY_PRODUCTION` variable decrypts. An application started with
the printed command receives the ciphertext as its secret, silently. Root-level
`.env` files are unaffected (keys file and env file share a folder), which is
why the end-to-end tests and the real-tool run B1 did not show it.

Fix: when a keys file is not in the same folder as an env file, print
`dotenvx run -f <env> -fk <keys> -- <cmd>` (or encrypt with
`-fk <env folder>/.env.keys` so the key lands beside the file; the script
already handles several keys files). More importantly, verify every encrypted
key by decrypting it (`dotenvx get KEY -f <env> -fk <keys> --overload`) before
declaring success: that check would have caught this and S1-1.

### S3-1. UTF-8 BOM in `.env` misclassifies the first entry

`parse_env_entries()` does not strip `﻿`, so line 1 is not an entry. The
secret becomes a "source" item whose store is the same file. With the fake
dotenvx the result is `STRIPE_SECRET_KEY=${STRIPE_SECRET_KEY}` on line 1 plus a
duplicate encrypted entry. With real dotenvx (which does handle the BOM) both
lines end up encrypted but the summary says `Done: 0 secret(s) encrypted`.
Notepad still writes BOMs. Fix: strip the BOM before parsing, which makes the
entry an `env` item that `execute()` already marks done once its key is
encrypted. Do **not** count a `source` item as done when its rewrite found
nothing: that "skipped" status is the only signal that the file changed
between scan and rewrite and may still hold the plaintext in another form.
Instead make the summary report "stored encrypted" and "plaintext removed"
as separate counts so a skipped rewrite is visible rather than miscounted.

### S3-2. A symlinked store `.env` (or `.gitignore`) is replaced by a regular file

`load_for_edit()` refuses symlinked source files, but the store path and
`.gitignore` are written through `write_bytes()` (temp + rename), which replaces
the link with a regular file and leaves the target unchanged. Reproduced.
Fix: `os.path.realpath()` the store and `.gitignore` before writing, or refuse.

### S3-3. Plaintext is staged into the real `.env` before dotenvx runs

`encrypt_env_file()` appends `KEY='plaintext'` to the real file, then runs
dotenvx. A hard kill (SIGKILL, power loss, OOM) during dotenvx leaves the secret
in two places. A kill between `mkstemp` and `rename` leaves
`.sweep-and-secure-XXXX` holding plaintext; on the next run that file is scanned
and treated as a source file (reproduced). Fix: stage into a copy that keeps
the **exact basename**, inside a temporary directory under the project
(`<root>/.sweep-and-secure-XXXX/.env.production`), run
`dotenvx encrypt -f <copy> -k KEY... -fk <root>/.env.keys`, verify, then
atomically rename the copy over the real path. Two constraints were measured
with dotenvx 2.38.2 and must be respected:

- dotenvx derives the key variable names from the file's basename. Encrypting a
  copy named `.sweep-and-secure-tmp` produced `DOTENV_PUBLIC_KEY_` and
  `DOTENV_PRIVATE_KEY_` (empty suffix); after renaming it to `.env.production`,
  `dotenvx get` silently returned the ciphertext instead of the value. The
  same-basename copy produced `DOTENV_PRIVATE_KEY_PRODUCTION` and decrypted.
- `dotenvx encrypt --stdout` leaves the file untouched but never writes
  `.env.keys`, even with `-fk`, so a newly generated private key is lost. It is
  usable only as a second step after the key pair exists (bootstrap with a plain
  `dotenvx encrypt -f <real file>` while it holds nothing to encrypt, which adds
  only the public-key header). The rename recipe above needs no bootstrap.

The `# -fk ../.env.keys` hint dotenvx writes into the copy may be stale after
the rename; measured, `get` and `run` do not use it for lookup (see S2-4), so
it is cosmetic, but the script can rewrite it since it already parses it.
Also add `\.sweep-and-secure-` to the default excludes and remove stale temp
files at start.

### S3-4. `.env.example`, `.env.sample`, `.env.template`, `.env.dist` are real env files to the script

A secret-shaped value in `.env.example` is listed as "encrypt in place", and
`--env-all` would encrypt every example placeholder and add a public key to the
example file. Fix: list these under manual attention or at least label them.

### S3-5. Child process is not killed on interrupt

`run_command()` has no `try/except` around `communicate()`. On an interrupt the
Python side restores `.env` while dotenvx may still be writing it (no terminal
means the child did not get the signal). Fix: `kill()` and `wait()` the child
before restoring.

### S3-6. Findings are not checked against the exclude list

`build_plan()` trusts TruffleHog to have honoured `--exclude-paths`. On Windows
(W1 below) it does not, so a finding under `.git/` or `node_modules/`, or in
`.env.keys`, would be rewritten. Fix: `is_excluded()` guard in `build_plan()`.

### S3-7. A tool whose `--version` fails is accepted

`tool_version()` returns `(None, error)` and `locate_tools()` only rejects
`version is not None and version < min`. The failure then surfaces mid-run.
Fix: refuse unless an override flag is given.

### S3-8. `write_bytes()` guarantees are weaker than documented

If `mkstemp` fails the fallback is a non-atomic truncate-and-write (the
docstring says an interrupt can never truncate a file). `copymode` keeps the
mode but drops owner, group, ACLs, xattrs and SELinux context (relevant when run
with sudo); rename breaks hard links. Fix: best-effort `copystat`/`chown`,
and in the fallback keep the original bytes in memory and restore on failure.

### S4. Minor

- No top-level catch-all in `main()`: any unexpected exception is a bare traceback.
- `sys.stdin` can be `None` (pythonw, some services): `confirm()` raises.
- The UTF-16 branch in `locate()` is unreachable: `load_for_edit()` rejects any
  file containing NUL bytes, which every UTF-16 file does.
- Byte substitution in length-sensitive formats (uncompressed PDF without NULs,
  lockfiles with registry tokens) can corrupt them; consider a warn-list.
- `.gitignore` with CRLF gets LF lines appended.
- "Interrupted; nothing further was changed" is printed even when things were.

## 4. Is the testing sufficient? No, not for a tool that destructively rewrites credential files

What is good: realistic end-to-end fixtures; snapshot-based "unchanged"
assertions; tests for dotenvx failure, dotenvx no-op, TruffleHog failure and
partial failure, interrupt during encryption, atomic write, gitignore negation;
no secret-shaped strings committed. 87% line coverage once subprocess runs are
counted.

What is missing:

1. **Failure paths** (the 13% uncovered is almost entirely error handling):
   unreadable or vanished files, oversized files, symlinks, restore failure,
   `.gitignore` write failure, bad `--exclude` regex, non-folder path, non-git
   folder, tracked `.env.keys`, `discover_keys_files` hint path, EOF on prompt.
2. **The defects above**: multi-key same value, re-run idempotency, BOM, CRLF
   (there is no CRLF test at all), symlinked store, non-UTF-8 stdout, inexact
   quoting round trip.
3. **Fake fidelity**: the fake dotenvx never expands `$`, never keeps `\"`
   literal, never lets `os.environ` win, never prints non-ASCII; the fake
   TruffleHog detects strings the real one rejects. S1-1 and S2-1a are
   invisible to the suite by construction. Add an opt-in tier that runs the
   suite against the real tools when they are on `PATH`, and a round-trip
   property test of `quote_env_value` against real dotenvx for a corpus of
   awkward values.
4. **No CI**, so nothing runs on Windows, macOS, or Python 2.7. The fake tools
   have `python3` shebangs, so the suite cannot run on a 2.7-only machine.
5. No unit tests for `execute()` job assembly, `assign_names()` collisions
   (`_2` path uncovered), `inventory_env_files`, `ensure_gitignore` without git.

## 5. Does it work on all main OSes and versions?

| Platform | Status |
| --- | --- |
| Linux, Python 3.8 / 3.11 / 3.12 / 3.13 | Verified here with fakes and with real tools (3.13) |
| Linux, Python 2.7 | Unverifiable here; static scan clean; README claim unproven. Recommend dropping 2.7 (EOL 2020) rather than carrying `PY2` branches nobody tests |
| macOS | Not run. No blocker found. Case-insensitive FS: `is_env_file` misses `.ENV`; README's `python` command does not exist on stock macOS |
| Windows | Not run. Four concrete problems found by reading CPython and TruffleHog sources, below |

Windows findings (reasoned, not executed):

- **W1** `DEFAULT_EXCLUDES` use `/`. TruffleHog's filter runs each regex on the
  native `filepath.Join` path with no slash normalisation (`pkg/common/filter.go`,
  `pkg/sources/filesystem/filesystem.go`), so `.git`, `node_modules`, venvs and
  `.env.keys` are all scanned on Windows. Combined with S3-6, findings there
  would be rewritten. Use `[/\\]` in the patterns.
- **W2** `find_tool` adds `node_modules/.bin/dotenvx`. On Python 3.8 to 3.11
  `shutil.which` with a directory component ignores `PATHEXT` and returns the
  extensionless POSIX shim; `Popen` fails with `WinError 193`, `tool_version`
  swallows it, the tool is accepted (S3-7) and encryption fails later. Prefer
  `dotenvx.cmd` on `nt`. Python 3.12+ handles this.
- **W3** Console encoding: redirected output is cp1252; dotenvx's glyphs trigger
  S2-1a whenever `-v` is used.
- **W4** `os.replace` fails on a file open in another process (editor,
  antivirus). Handled for sources, but inside `restore_file` it becomes S2-1b.
- No long-path (`\\?\`) handling; `mkstemp` in deep trees falls back to the
  non-atomic write.

## 6. Notes on dotenvx behaviour that the fix must respect

Measured on 2.38.2: single quotes are fully literal; backticks are literal except
`$name` expansion (`\$` escapes it); double quotes expand `$name`, `\n`, `\t`,
honour `\$`, and keep `\"` and `\\` literally. Duplicate keys: last wins for
`get`, and `encrypt -k` encrypts every occurrence. `get` and `decrypt --stdout`
let an existing `os.environ` variable override the file unless `--overload` is
given, so any verification step must pass `--overload` or clear the
environment. `.env.keys` is written to the cwd with mode 0600 and the env file
gets a `# -fk ../.env.keys` hint; `discover_keys_files` handles both. `get`,
`run` and `keypair` do not use that hint: they look for `.env.keys` beside the
env file, so nested env files need an explicit `-fk` (S2-4). Key variable
names come from the env file's basename (S3-3).

## 8. Resolution

Every item above is addressed in the commit that follows this section's addition
(same pull request). Where the fix differs from what section 3 proposed, the
measured behaviour that forced the change is noted.
